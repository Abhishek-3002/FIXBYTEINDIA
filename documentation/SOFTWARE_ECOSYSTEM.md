# FIXBYTE INDIA — Software Ecosystem

## Mission
Build FIXBYTE INDIA into a product studio that can design, build, test, distribute, license, update, and support its own web, Windows/macOS desktop, and Android/iOS products.

This document is the architecture and delivery baseline. It is not a claim that these systems are already implemented.

## Product lines
1. Web applications and SaaS products.
2. Desktop applications: Windows first; macOS after the Windows release pipeline is stable.
3. Mobile applications: Android first; iOS after platform signing and store workflows are ready.
4. Software marketplace: product pages, demos, pricing, customer accounts, downloads, release notes, and support.

## Recommended technical baseline
- Web UI and customer/admin portals: React + TypeScript + Vite.
- Desktop shell: Tauri 2, with Rust commands only where native capabilities are required.
- Mobile: evaluate React Native/Expo for cross-platform apps; choose native modules only when required.
- API: Node.js + TypeScript (Express or Fastify) with versioned REST endpoints.
- Database: PostgreSQL for hosted multi-tenant data; SQLite for local-first desktop data.
- Data access: migrations, schema validation, and typed repository/service layers.
- Authentication: secure server-side sessions or short-lived access tokens with refresh-token rotation; never store passwords or long-lived secrets in the client.
- File delivery: object storage/CDN for signed installers and release assets.
- CI/CD: GitHub Actions for lint, type-check, tests, builds, and release artifacts.
- Hosting: deploy the web/API components to a suitable managed host; Vercel can host the web front end, but persistent databases and file storage must use dedicated services.

## Core platform modules
1. Identity and access: customer accounts, staff/admin roles, MFA option, session revocation.
2. Product catalogue: product metadata, plans, supported platforms, requirements, screenshots, changelog.
3. Licensing: product-specific entitlements, activation/deactivation, device limits, trial/expiry, grace period, offline license cache with signed claims.
4. Billing: payment-provider integration, verified server-side webhooks, invoices/receipts, refunds and plan changes. Never trust a client-reported payment success.
5. Downloads and releases: versioned artifacts, checksums, code-signing status, release channels (stable/beta), signed download URLs.
6. Updates: update manifest, staged rollout, rollback strategy, signature verification before installation.
7. Support: tickets, diagnostics consent, product/version/device details, knowledge base.
8. Telemetry: opt-in, privacy-minimized crash/error reporting; no collection of customer business data by default.
9. Admin console: manage products, releases, customers, entitlements, support, and audit events.
10. Backup and recovery: automated database backups, restore drills, retention policy, export tools.

## Desktop application standard
- Windows installer: signed MSI or NSIS setup executable generated by Tauri.
- macOS packaging/signing/notarization is a separate release track.
- Local data must be encrypted where appropriate and protected by OS permissions.
- Offline-first features must define conflict resolution and sync retry behavior.
- Updates must verify signatures and support safe rollback.
- Do not claim an app is fully offline if login, licensing, or core workflows require network access.

## Security and compliance baseline
- Keep API keys, signing keys, database credentials, and payment secrets on the server or in CI secret storage.
- Use HTTPS, least-privilege roles, input validation, output encoding, rate limits, and audit logs.
- Use parameterized database queries and tested migrations.
- Add dependency scanning, secret scanning, and build provenance where practical.
- Publish a privacy policy, terms, refund/cancellation policy, EULA, and product-specific data handling notice before public sales.
- Obtain appropriate code-signing certificates before distributing production installers; unsigned builds may trigger Windows security warnings.
- Licensing and terms reduce risk but cannot guarantee immunity from legal claims or government notices. Obtain qualified legal review for each product and jurisdiction.

## Repository strategy
- Keep the current public website stable.
- Use a dedicated branch for ecosystem foundations and review changes before merging.
- As the codebase grows, split independently deployed products/services into separate repositories when that improves access control and release isolation.
- Never commit .env files, credentials, customer data, signing certificates, or private keys.

## Delivery phases
### Phase 0 — Foundation
- Confirm repository and deployment ownership.
- Establish architecture, branch protections, coding conventions, CI checks, issue templates, and secrets policy.
- Add a small working desktop proof-of-concept and verify local Windows packaging.

### Phase 1 — Reusable product starter
- Desktop starter shell, navigation, settings, local SQLite storage, migrations, logging, and tests.
- Web/API starter with health endpoint, authentication boundaries, PostgreSQL migrations, and API validation.
- Shared product metadata and release conventions.

### Phase 2 — Platform services
- Customer portal, admin console, product catalogue, licensing API, download service, and support workflow.
- Payment integration only after server-side webhook verification and test-mode validation.

### Phase 3 — Release engineering
- Automated Windows builds, checksums, signed release manifests, beta/stable channels, update checks, and rollback testing.
- Publish downloads only after malware scanning, smoke tests, and release approval.

### Phase 4 — First real product
- Select one small business use case.
- Define requirements, data model, threat model, acceptance tests, backup/export, and support plan.
- Pilot with a small number of users before general release.

### Phase 5 — Marketplace and scale
- Public product pages, plans, customer downloads, license self-service, release notes, and support.
- Add macOS/mobile pipelines after the first desktop product is stable.

## Definition of done for a production release
- Requirements and acceptance criteria approved.
- Unit, integration, and smoke tests pass.
- Database migration and backup/restore tested.
- Security and dependency checks reviewed.
- Installer tested on a clean supported Windows machine.
- Update and rollback paths tested.
- License/payment flows verified server-side.
- Privacy, terms, support, and release notes published.
- Version, checksum, and signed artifact recorded.
